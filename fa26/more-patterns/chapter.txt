## [Stopping When You're Done](early-return.html)

Student: Professor, I noticed that a program I wrote is doing too much work.

Prof: Too much work?

Student: Yeah, I wrote a kind of best-so-far loop, I think, but it’s really more of a “found so far” loop:

```java
boolean anyContains(String[] words, String part) {
  boolean found = false;
  for (String w : words) {
    System.out.println("checking " + w);
    if (w.contains(part)) {
      found = true;
    }
  }
  return found;
}
String[] animals = { "cat", "dog", "bird", "fish" };
boolean b = anyContains(animals, "a");
```

Prof: Looks like it works, right?

Student: Sure, but look at the printout. It is **also** looking at `"dog"` and `"bird"` and `"fish"`. How can I make it not do that?

Prof: Ah, you want an early return.

Student: An early return?

Prof: Once you have found a matching string, you want the method to return, it sounds like. So instead of updating `found = true`, you can just directly `return` there:

Student: Like this?

```java
boolean anyContains(String[] words, String part) {
  boolean found = false;
  for (String w : words) {
    System.out.println("checking " + w);
    if (w.contains(part)) {
      return true;
    }
  }
  return found;
}
String[] animals = { "cat", "dog", "bird", "fish" };
boolean b = anyContains(animals, "a");
```

Student: Oh, and now only `"cat"` prints. Yeah, that’s what I wanted. Wait, now the `found` variable is really weird, right? Nothing sets it.

Prof: That’s right – I don’t think you need it anymore.

Student: But what will I return at the end?

Prof: What was the value in `found`?

Student: So I just return `false`?

Prof: Makes sense to me – if the loop runs through all the elements without any containing `part`, then return `false`. The loop **would have returned** if any element matched, so if control reaches the end of the loop, returning `false` is correct.

Student: Huh, that seems a lot simpler.

```java
boolean anyContains(String[] words, String part) {
  for (String w : words) {
    System.out.println("checking " + w);
    if (w.contains(part)) {
      return true;
    }
  }
  return false;
}
String[] animals = { "cat", "dog", "bird", "fish" };
boolean b = anyContains(animals, "a");
```

Prof: I’d call this a search loop. It searches for something matching a pattern, and stops as soon as it finds it and returns `true`. You could return other values, too, like using `return w` in the loop to return the found string. That would change the return value, and you’d need to think through what the final `return` should be.

It’s also using an important idea called an early return. That’s a `return` statement that runs in the middle of a loop or other block of code. A `return` **always** immediately exits the current method with the given return value. So the rest of the loop, or any later statements, never run.

Student: Neat, a search loop with an early return. Is it faster?

Prof: Yeah, you could say we just “optimized” your program a little bit – we made it take fewer steps for some kinds of inputs. Nice work!

Here are two methods that search an array for a string containing `part`. One uses an early return. The other keeps a found-so-far variable and returns it after the loop.

```java
String withReturn(String[] words, String part) {
  for (String w : words) {
    if (w.contains(part)) {
      return w;
    }
  }
  return "";
}

String withFlag(String[] words, String part) {
  String found = "";
  for (String w : words) {
    if (w.contains(part)) {
      found = w;
    }
  }
  return found;
}
```

Prof: Here’s what Pict did.

```java
default Raster render() {
```

```java
interface DriveItem {
```

Prof: Just so. This is called the accumulator pattern. Sometimes we need to pass along an argument through a recursive structure, rather than trying to return the answer. It’s the same idea as the running-sum and best-so-far accumulators from our loops. Those were local variables, but every call gets its own locals, so here the accumulator has to be passed along. We build it up in the argument position, and that position is called an accumulator parameter!

Student: Neat, I can feel the knowledge accumulating!

Prof: Wow, um, maybe leave the puns to me.

Prof: Now, let’s think about what happens in `totalLikes()` for that reference. What gets called?

Prof: Right. And what happens in that call?

Student: Wait, it’s going to keep going back and forth between `@1001` and `@1003`? Why?

Prof: That’s just what the code does – it keeps going into the loop for the calls on `@1001`, and finding the `replyTo` field on `@1003`, which calls back to `@1001`.

Student: So it’s like an infinite loop, but with recursion?

Prof: Right. We call it unbounded recursion or infinite recursion. It ends when the stack runs out. In this book that gets reported as an `ArithmeticException`, in your terminal it would report as a `StackOverflowError`. It happens when a method calls back to itself with the same arguments, and nothing has changed to stop it from doing the same calls again.

Student: So how do we write `totalLikes` if the normal recipe doesn’t work?

Prof: I think we need to say more what we **want** `totalLikes` to do! I think there are two different total likes definitions we could mean.

Student: Two different ones?

Prof: Right – do we want to know the likes **in this post and its replies**, or **in this post and the posts it is replying to**? Does it go “down” through all the replies, or “up” through what it is replying to?

Student: Hmm, and what changes?

Prof: Well, going through the replies only recurs on the `replies` field. Going the other way recurs only through the `replyTo` field.

A base case is a call that makes no more recursive calls. Use the memory picture above.
