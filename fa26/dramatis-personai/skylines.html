A Program to Check a Program

Student: OK. So contains passes all the tests but you still don’t trust it? Why not?
Prof: Well, we wrote a dozen or so tests. I feel like there’s a lot of ways for it to be wrong. Like, what if you make a spiral shape, or there are some weird funky corners like in those shapes on the original map? Does it always work? Like always? Would you trust it to tell someone if they are in a fire evacuation zone?
Student: I guess I can see that. So do we write more and bigger tests?
Prof: We run more tests. But I don’t want to write them.
Student: So we will ask AI to write them?
Prof: No, I wouldn’t be happy with that. We’d have the same trust in the tests as we do in the code, and I wouldn’t really be able to read all of them to check. So we’d have AI checking AI, which doesn’t improve my confidence.
Student: So what do we do?
Prof: We’ll write a second, small program, and its whole job will be to check the first one.
Student: A program that tests a program?
Prof: Yes. Let’s think about what one of our tests is made of: a shape, a point, and the answer we expect. So far all three came from us, thinking hard about shapes and drawing pictures. But programs are really good at generating lots of data!
Student: It can make up shapes and points, sure. But the expected answer? Isn’t that… contains? The thing we’re testing?

Prof: It shouldn’t come from the same code, no. But look at this shape, described two ways:

three rectangles
one outline
Student: The left one is three RectRegions in a Union. The right one is a Polygon with eight points.
Prof: Do you trust RectRegion and Union?
Student: Yeah. Each one is a line or two, and we wrote them ourselves.
Prof: Then for this shape, the rectangles can tell us what the polygon should answer, at any point we like. Code that supplies the expected answers for a test is called an oracle.
Student: For this one shape, though.
Prof: Any row of columns works the same way. Let’s call a row of columns standing on the x-axis a skyline. To keep things simple, every column in a skyline has the same width. So a skyline is a width and an array of heights. This one is width 2 with heights { 3, 5, 2 }. We need two methods that take the same width and heights. One builds the rectangles, and the other builds the outline. Start with the rectangles.

Student: That’s an accumulator:

// the same columns, as one RectRegion each
Region skylineRects(int width, int[] heights) {
  Region columns = new RectRegion(new Point(0, 0), width, heights[0]);
  for (int i = 1; i < heights.length; i += 1) {
    columns = new Union(columns,
        new RectRegion(new Point(i * width, 0), width, heights[i]));
  }
  return columns;
}
Prof: Do you believe it?
Student: For { 3, 5, 2 } it makes a rectangle at x = 0 that’s 3 tall, one at x = 2 that’s 5 tall, and one at x = 4 that’s 2 tall. That’s the green picture. Yes, it’s definitely right.

Prof: Now let’s do it as a polygon. That one is harder to see, so build it up one column at a time:

heights { 3 }
{ 3, 5 }
{ 3, 5, 2 }

What changes each time a column is added?

Student: Two new points show up, the new column’s top-left corner and its top-right corner. Those are 3 and 4, and then 5 and 6. The last point, at the bottom right, slides over. And point 0 is always (0, 0).
Prof: So where in the array do column i’s two corners go?

Student: Column 0 gets 1 and 2. Column 1 gets 3 and 4. Column 2 gets 5 and 6. So 2 * i + 1 and 2 * i + 2. And the array needs two points for each column, plus the two on the bottom.

// columns of the same width, standing side by side on the x-axis
Polygon skyline(int width, int[] heights) {
  Point[] outline = new Point[2 * heights.length + 2];
  outline[0] = new Point(0, 0);
  for (int i = 0; i < heights.length; i += 1) {
    outline[2 * i + 1] = new Point(i * width, heights[i]);        // top-left of column i
    outline[2 * i + 2] = new Point((i + 1) * width, heights[i]);  // top-right of column i
  }
  outline[outline.length - 1] = new Point(heights.length * width, 0);
  return new Polygon(outline);
}

Prof: Pin it down with the picture as an example. Outlines are arrays, so this needs assertArrayEquals:

assertArrayEquals(
    new Point[] { new Point(0, 0), new Point(0, 3), new Point(2, 3), new Point(2, 5),
                  new Point(4, 5), new Point(4, 2), new Point(6, 2), new Point(6, 0) },
    skyline(2, new int[] { 3, 5, 2 }).outline());
How many points are in the outline that skyline(5, new int[] { 10, 20, 10, 30 }) returns?

Prof: Now the points. Where should the program check?
Student: Lots of places. Inside, outside. And right on the edges and corners, like we had.

Prof: A grid does all of that:

what the rectangles say
what the outline should say

Each dot is a point we can ask contains about. A filled dot means the answer ought to be true. We’re going to write a program that will check that every one of these points gets the same answer for both ways of constructing the shape. In just a few lines, it would look like this:

int checkSkyline(int width, int[] heights) {
  Polygon outline = skyline(width, heights);
  Region rects = skylineRects(width, heights);
  int checks = 0;
  for (int i = 0; i < 100; i += 1) {
    for (int j = 0; j < 100; j += 1) {
      Point p = new Point(-5 + i * 0.5, -5 + j * 0.5);
      assertEquals(rects.contains(p), outline.contains(p), "at " + p);
      checks += 1;
    }
  }
  return checks;
}
Student: OK so given a width and heights, we make two shapes, and check that a bunch of points are in both of them? What if one of the points isn’t in one of them?
Prof: That’s expected! There are lots of dots on the grid outside of both shapes. In that case the assert will compare false == false: they get the same answer, which is correct!
Student: Oh and you put the rects one as the expected value. So whatever it says is what we expect the complicated AI one to do!
Prof: Exactly right. And we can make really big grids, like 100×100 points at 0.5 increments.
Student: Why 0.5?
Prof: You could make many choices here. It makes sure we hit edges and spots within the shapes. But you could try other values!
Student: So what would it look like if something goes wrong?

Prof: There would have to be a mismatch. It could be our fault, like making a skyline wrong, so the two shapes don’t look the same:

an outline with a mistake

The red dots are the grid points where the two sides disagree. The assertion would stop at the first one and name it.

Suppose an assertion in checkSkyline fails. What do we know?
  1. The two sides disagree at that point. The mistake could be in contains, in skyline, or in skylineRects, and we’d have to look at the point to find out which.
  2. Polygon’s contains has a bug.
    It might. But the test only shows that two answers differ. In the picture above, contains could be answering correctly for an outline that skyline built wrong.
  3. skyline built the wrong outline.
    That’s the picture above, but it isn’t the only way to get red dots. A mistake in contains or in skylineRects would also make the two sides disagree.
Prof: One more thing about skylines. What happens to the outline when two neighboring columns are the same height?
Student: Then the top-right corner of one is the top-left corner of the next. The same point is in the array twice! Is contains OK with that?
Prof: I don’t know.
Student: …So we put one in the checks. Heights { 9, 9, 5 }.
Prof: Good. We’re still picking every skyline by hand, though.
Student: So have the computer pick?
Prof: Yes, here I’d actually be OK asking AI to generate a bunch of skylines for us to use, because I just want a wide variety! I’m equally confident in the checks in checkSkyline for any skyline we come up with, and any weird mismatches will fail an assertion. But there’s another way to generate skylines – randomly!
Student: Randomly?

Prof: Yes. Randomized testing is actually a commonly used, and effective, kind of generator. Java’s Random hands out numbers that look random: random.nextInt(6) gives one of 0 through 5. The number we give to new Random(...) is called a seed. The same seed gives the same numbers on every run, so a check that fails today fails the same way tomorrow. A different seed gives a different batch of skylines. That’s why the seed is a parameter here: main picks one, and we can try another any time we like. A method that makes up test inputs like this is called a generator.

int checkRandomSkylines(int count, int seed) {
  Random random = new Random(seed);
  int checks = 0;
  for (int s = 0; s < count; s += 1) {
    int width = 1 + random.nextInt(7);
    int[] heights = new int[1 + random.nextInt(6)];
    for (int i = 0; i < heights.length; i += 1) {
      heights[i] = 1 + random.nextInt(40);
    }
    checks += checkSkyline(width, heights);
  }
  return checks;
}
Prof: Here is the whole checking program. The body of contains is folded shut: it’s the thing being tested, and nothing here depends on reading it. Everything else is ours.

Practice
The program printed “240,000 checks passed”. Which of these did it actually check?
  1. A skyline where two neighboring columns are the same height
  2. Points exactly on the corners and edges of a skyline
  3. A skyline with ten columns
    checkRandomSkylines makes between 1 and 6 columns, and the skylines we picked by hand have at most 4.
  4. The point (0.25, 0.25)
    Every grid point is a multiple of 0.5, so a point like this one is never asked about.
  5. A shape with a slanted side
    Every edge of a skyline goes straight up or straight across.
