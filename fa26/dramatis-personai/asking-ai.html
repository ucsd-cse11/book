Claude: Pass by value

The function receives a copy of the argument’s value. The parameter is a new, independent variable initialized with that value. Assigning to the parameter inside the function has no effect on the caller’s variable.

void f(int x) { x = 10; }

int a = 5;
f(a);
// a is still 5

Pass by reference

The function receives a reference to the caller’s variable itself, not a copy of its value. The parameter becomes an alias for the caller’s storage location, so assigning to the parameter changes the caller’s variable.

void f(int& x) { x = 10; }

int a = 5;
f(a);
// a is now 10

A useful test: can you write a swap(a, b) function that exchanges the contents of the caller’s two variables? With pass by reference, yes. With pass by value, no.

The common confusion: passing references by value

Languages like Java, Python, JavaScript, and Ruby are often described as pass by reference, but they are pass by value. The value being copied just happens to be a reference (pointer) to an object. This is sometimes called call by sharing or call by object reference.

def f(lst):
    lst.append(4)   # mutates the shared object; the caller sees it
    lst = [99]      # rebinds the local parameter; the caller does NOT see it

a = [1, 2, 3]
f(a)
# a is [1, 2, 3, 4]
  • Mutation is visible because the caller and the callee both point to the same object.
  • Reassignment is not visible because the parameter is a copy of the pointer, not an alias for the caller’s variable a.

So the key question is not “can the function change the object?” It is “can the function change which value the caller’s variable holds?” Only true pass by reference allows that.

Note that C’s “pass a pointer” (void f(int *p)) is pass by value of a pointer. It simulates pass by reference, but the pointer itself is still copied.

The definitions

Pass by value: When you call a method, each parameter gets a copy of the argument’s value. If the method assigns a new value to the parameter, only the method’s own copy changes. The caller’s variable stays the same.

Pass by reference: The parameter becomes another name for the caller’s variable itself. If the method assigns to the parameter, the caller’s variable changes too. C++ (int&) and C# (ref) can do this.

Which one Java uses

Java always passes by value. The confusing part is that for arrays, Strings, and objects, the value being copied is a reference like @1001. The glossary already says this: a value is “anything that can be stored, passed, or returned, including primitives and references.” When you call a method, the reference is copied into the method’s stack frame, not the object.

So when people say “Java passes objects by reference,” it’s loose wording. What really happens is that the reference is passed by value. Two experiments show the difference:

void zeroFirst(int[] arr) {
  arr[0] = 0;               // changes the array on the heap
}

void replace(int[] arr) {
  arr = new int[]{ 9, 9 };  // changes only this frame's copy of the reference
}

void main() {
  int[] nums = { 6, 7 };    // nums = @1001
  zeroFirst(nums);          // arr = @1001 (a copy of the reference)
  replace(nums);            // arr = @1001, then arr = @1002
  System.out.println(Arrays.toString(nums));  // [0, 7]
}

In a memory diagram like the book’s:

  • zeroFirst: nums and arr hold the same reference, @1001. This is aliasing, from the Aliasing section: “updates through one reference are visible through all the others.” The caller sees 0. This is why discountInPlace() works.
  • replace: The assignment only changes arr in replace’s stack frame to @1002. nums in main’s frame is still @1001. If Java passed by reference, nums would now be [9, 9]. It isn’t.

Primitives work the same way. void addOne(int n) { n = n + 1; } never changes the caller’s variable, because n is a copy.

The short version for the student

Java copies whatever is in the variable. For an int, that’s the number. For an array or object, it’s the reference (the @1001). Changing the object through the copied reference is visible to the caller. Changing the parameter to point somewhere else is not.

Claude: Pass by value vs. pass by reference

Both terms describe what a method’s parameter is when you call the method.

Pass by value: The method gets a copy of the value of each argument, stored in a new variable in the method’s own stack frame. If the method assigns a new value to its parameter (param = ...), the caller’s variable doesn’t change.

Pass by reference: The parameter is another name for the caller’s variable itself. If the method assigns to the parameter, the caller’s variable changes too. Java doesn’t have this, but some languages do, such as C++ (int& x) and C# (ref int x).

What Java does

Java is always pass by value. The confusion comes from what the value is:

  • For a primitive like int, the value is the number, such as 17.
  • For a reference type (arrays, String, records, classes), the value is a reference, like the @1001 in the book’s memory diagrams.

So when you pass an array, Java copies the reference into the new stack frame. The caller and the method then hold the same reference. That is aliasing, from the “How Java Runs” chapter. This program shows both effects:

void change(int n, int[] arr) {
  n = 99;               // changes only this frame's copy of n
  arr[0] = 99;          // changes the array on the heap: the caller sees it
  arr = new int[]{ 0 }; // changes only this frame's copy of the reference
  arr[0] = -1;          // changes the new array, which the caller never sees
}

void main() {
  int x = 5;
  int[] nums = { 1, 2, 3 };
  change(x, nums);
  System.out.println(x);        // 5
  System.out.println(nums[0]);  // 99
}

Here’s what memory looks like right after the line arr[0] = 99; runs:

main()                 x = 5, nums = @1001
change(x, nums)        n = 99, arr = @1001

Heap
@1001: [99, 2, 3]

Only one array exists, and both frames refer to it. The next line, arr = new int[]{ 0 };, gives arr a new reference, @1002. The nums variable in main still holds @1001. If Java were truly pass by reference, that assignment would have changed nums too.

When an AI says “Java passes objects by reference,” it usually means “methods can change objects you pass to them.” That’s true, but it’s because the method gets a copy of a reference, not because Java has pass by reference. Some people call this “passing references by value.” To predict what a program will do, draw the memory diagram: a new frame, with copies of the argument values in it.

Claude: To figure out what a call can change, draw the frames:

  • The method can’t change the variables in the caller’s frame.
  • It can change anything on the heap that it can reach through the references it was given, unless those objects are immutable, like records or Strings.

Is that last part the right way to think about records and immutability? Think about addOne here. Which of the statements below is true?

record Bag(int[] counts) { }
void addOne(Bag b) {
  b.counts[0] = b.counts[0] + 1;
}
  1. addOne can change the contents of the array that b.counts refers to. The array can be “reached” from an addOne frame, and it can be changed.
  2. A record can’t change because it is “immutable”, so Java will report an error in addOne.
    A record’s fields can’t be reassigned, but the array in counts is a separate object on the heap. addOne compiles, and it changes that array.
  3. addOne could make b.counts hold a new array, so the record is mutable, not “immutable” as claimed.
    Record fields can’t be reassigned: b.counts = new int[]{ 0 }; is a compile error. The change in addOne is to the array, not the field.

A quick definition: Java calls records shallowly immutable, which means they only prevent field update, not changes to objects or arrays they reference.
