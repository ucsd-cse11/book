Structuring Code Generation

Student: How should I structure code generation with AI?
Prof: First of all, great question. Second, pretty much the entire field of software engineering is working on answering this question; there’s no “best” or “right” answer. Programmers will be finding their own answers to this for a long time.
Student: OK, fine, but like, what should I do? Give me some advice!

Prof: Early on we talked about the “design recipe”:

  1. Define the data and write examples to make the representation clear
  2. Identify the method you want to write
  3. Write the method header and examples together to figure out what it’s supposed to do; placeholder values to make it run
  4. Implement the method body and check it against the examples.

I think it’s useful to think about which of these steps are good to have completed for you, and which are good to think through yourself.

Student: Hm so you’re going to say we should always define the data and come up with examples ourselves first?
Prof: I don’t think it’s a bad idea! But not that you have to do that all yourself – you could also ask a coding assistant for help with each step. Like maybe a model has a great suggestion for how to represent data in your problem; it’s just helpful to know that you’re on that step. It’s a way to structure the problem you’re trying to solve.
Student: I’m not sure I get it, can you give me an example?
Prof: OK, let’s try a more sophisticated program, and see if we can figure out the boundary between steps. We can start with something I think we will understand right away; a Region interface that checks if a Point is contained inside it, and several simple shapes
Student: Sure, seems familiar enough, we’ve seen lots of examples like this.

Practice
Before we write contains, here are two tests for lShape:
Polygon lShape = new Polygon(new Point[] {
  new Point(0, 0), new Point(0, 20), new Point(10, 20),
  new Point(10, 10), new Point(20, 10), new Point(20, 0) });

void main() {
  assertEquals(true, lShape.contains(new Point(5, 15)));   // in the tall part
  assertEquals(false, lShape.contains(new Point(25, 5)));  // off to the right
}
Which of these points would be useful to add as tests?
  1. (15, 15), in the corner the L leaves empty
  2. (15, 5), in the foot
  3. (6, 15), also in the tall part
    (5, 15) already tests the tall part. (6, 15) is in the same part for the same reason, so it’s unlikely to catch a mistake that (5, 15) misses.
  4. (30, 30), off to the upper right
    (25, 5) already tests a point off the shape entirely. (30, 30) is outside for the same reason: it isn’t near any part of the L.
  5. (10, 15), exactly on the edge between the tall part and the empty corner, once we decide what contains should say there
