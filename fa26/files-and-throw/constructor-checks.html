Checks in a constructor

Prof: Good memory! Yes, we can enforce that in the constructor of Gear itself, so that any attempt to create a Gear with a negative weight immediately throws an exception. That way, the data is always valid from the moment it’s created.
Prof: Recall what we did with Px.size in chapter 10. The Pict records call it in their constructors, so no circle can ever have a negative radius.
    /** A width, height, or radius: zero is fine (an empty picture), negative is not. */
    static int size(String what, int v) {
        if (v < 0) throw new IllegalArgumentException(what + " is negative: " + v);
        return v;
    }

Pict.java, lines 88–92

Prof: A circle hands its radius to Px.size, so no circle can ever have a negative radius:
record Circle(int radius, Color color) implements Pict {
    Circle { Px.size("radius", radius); }

Pict.java, lines 142–143

Student: So the check lives in the constructor — every circle gets checked when it’s made?
Prof: Exactly. And we can do the same thing for Gear. Gear { ... } is the constructor — the code that runs every time someone writes new
Gear(...). Put the check there, and no gear can ever have a negative weight. Gear has a quantity now, like the step-2 exercise — the check only cares about the weight:
record Gear(String name, double weightKg, int quantity) {
  Gear {
    if (weightKg < 0) {
      throw new IllegalArgumentException(name + " is negative: " + weightKg);
    }
  }
}
Student: There’s no what this time — the message just uses name.
Prof: Right. Px.size needed a what because it checked any number. A Gear object already knows its own name. Same message shape, though: “gloves is negative: −0.2”.
Student: And totalWeight doesn’t need its own check anymore?
Prof: It doesn’t — a bad gear can never exist now, so there’s nothing for totalWeight to catch. Every later new Gear(...) gets the check for free — including all the ones we’ll build from file lines in the next steps. Next, what if a line in the file has the wrong number of pieces?
