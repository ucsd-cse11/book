## [Self-Referential Data](naming-it.html)

Student: Professor, I want to get the hard stuff. The real stuff about programming, the can’t-fake-it, no-nonsense big ideas. Stuff like recursion. My friends in upper division classes are always talking about that.

Student: What?

Prof: We wrote our first recursive methods the last time we talked. And we’ve been making recursive data since we composed the French flag.

Student: How do you mean? Recursion is the hardest topic in CSE11. That’s what **everyone** says.

Prof: Then you’re doing great, as long as you understood our last conversations!

Student: Which parts?

Prof: Well, let’s bring up an example again and talk through a definition.

```java
record ImageData(String keywords, String fileType, int width, int height, int sizeKb) {}

interface ImageQuery {
  boolean matches(ImageData img);
}

record HasKeyword(String word) implements ImageQuery {
  public boolean matches(ImageData img) {
    return img.keywords().contains(this.word);
  }
}

record HasExtension(String ext) implements ImageQuery {
  public boolean matches(ImageData img) {
    return img.fileType().equals(this.ext);
  }
}

record SmallerThanKb(int limitKb) implements ImageQuery {
  public boolean matches(ImageData img) {
    return img.sizeKb() < this.limitKb;
  }
}

record And(ImageQuery left, ImageQuery right) implements ImageQuery {
  public boolean matches(ImageData img) {
    return left.matches(img) && right.matches(img);
  }
}

record Or(ImageQuery left, ImageQuery right) implements ImageQuery {
  public boolean matches(ImageData img) {
    return left.matches(img) || right.matches(img);
  }
}

ImageData img = new ImageData("cat sleeping", "png", 640, 480, 300);
ImageQuery cat = new HasKeyword("cat");
ImageQuery png = new HasExtension("png");
ImageQuery jpg = new HasExtension("jpg");
ImageQuery light = new SmallerThanKb(500);
ImageQuery pngOrJpg = new Or(png, jpg);
ImageQuery catPic = new And(cat, pngOrJpg);
ImageQuery query = new And(catPic, light);
boolean found = query.matches(img);
```

Output:

```text
img = ImageData[keywords=cat sleeping, fileType=png, width=640, height=480, sizeKb=300]
cat = HasKeyword[word=cat]
png = HasExtension[ext=png]
jpg = HasExtension[ext=jpg]
light = SmallerThanKb[limitKb=500]
pngOrJpg = Or[left=HasExtension[ext=png], right=HasExtension[ext=jpg]]
catPic = And[left=HasKeyword[word=cat], right=Or[left=HasExtension[ext=png], right=HasExtension[ext=jpg]]]
query = And[left=And[left=HasKeyword[word=cat], right=Or[left=HasExtension[ext=png], right=HasExtension[ext=jpg]]], right=SmallerThanKb[limitKb=500]]
found = true
```

Prof: So, in terms of definitions:

- The `And` record is a recursive datatype: it both implements `ImageQuery` and it has a field of type `ImageQuery`. That means a field of an `And` record can itself be an instance of `And`.
- The `matches` method is a recursive method: when it calls `matches` on its fields, it may be calling **the exact method it is in**. That is, two stack frames right next to each other, each for the exact same method of the exact same class, just different receivers.

These are the two important definitions of recursion in the object-oriented programs we will write.

Student: Huh. OK. So the memory trace would have multiple stack frames for the `matches` method on `And` at the same time?

Prof: Right, that’s the idea:

```
      img = @1001
      returns true

        returns true

          returns true

          returns true

            returns true

Heap
  @1001: ImageData[keywords=cat sleeping, fileType=png, width=640, height=480, sizeKb=300]
```

Student: Hm, ok so recursive data is when a record could have other instances of the same record in its fields? And recursive methods are when a method can call itself?

Prof: It’s frustrating right! There’s a good principle to learn here, though. All of the recursive data we’ve seen so far has a key feature: there are some records that have fields that refer back to the type, *and some that don’t*. For example in `ImageQuery`, the `And` and `Or` queries refer back to `ImageQuery`, but the ones that look directly at the image data like `HasExtension` or `HasKeyword` do not.

We call the ones with self-reference the recursive cases and the ones with no self-reference the base cases. What do you think some of the recursive and base cases of data are for `Pict`?

Student: Hmmm so I guess things like `Beside` are recursive cases, because they combine two `Pict`s and `Beside` implements `Pict`.

Prof: Right, and the base cases?

Student: Those must be the simple shapes like `Circle` and `Rect`.

Prof: Right. We don’t need to construct a `Pict` to pass into a `Circle`, and a `Circle` doesn’t store another `Pict`. So this idea of base cases and recursive cases comes up over and over again in representing interesting data.

Student: Really?

Prof: Yeah, I’ll give a few more examples:

- Math expressions like `(4 + 5) - x` → the base cases would be things like numbers and variable names. The recursive cases would be things like add and subtract expressions.
- Files and folders in Google Drive → folders would be the recursive cases (because folders contain files and folders) and files would be base cases (files can’t contain folders).
- Family trees of ancestors → people with known parents are the recursive cases (because they have parent fields that are also people), and the base cases are “unknown” places in the tree where there’s no information about an ancestor

Student: I’ll try one. In a course system, the courses are the recursive cases and the students in the course are the base cases.

Prof: Not quite! There’s no way for a course to contain a course, or a student to contain a student, so there’s no recursion in that example. It’s just nested data. That’s a really good example of the difference between data that is just nested, and data with a **self-reference**.

Student: Can I try another one?

Prof: Sure!

Student: OK so how about course prerequisites. An upper division course is a recursive case, because it has some prerequisites, like CSE12 requires CSE11, so CSE12 must have a field or something that stores CSE11. But CSE11 has no official prerequisites, so it is a base case?

Prof: Great example!

## [Building Up, with Code](base-case-code.html)

Student: So I feel like I get the **idea** of recursion, but I don’t know how to turn your examples into code.

Prof: Let’s get back to your original idea – how would this look for `Post`s, in code?

Student: Do I have to write an interface first?

Prof: That’s how we’ve been doing it; at some point I’ll show you another way, but for this example that’s a good idea.

Student: OK so I need… an interface that represents posts? And then a recursive case and a base case.

Prof: Right – so the recursive case is the one you started with.

Student: A repost?

Prof: Right. And if you think about how posts work, what has to be at the end of a long chain of reposts?

Student: A… regular post?

Prof: Right! OK try turning that into code.

Student: Hmm so something like this?

```java
interface Post {}
record Repost(String message, Post original) { }
record RegularPost(String message) { }
```

Student: OHH so the base case just has the text. Like when you make one Tweet or whatever. I guess real posts have more stuff like images.

Prof: Absolutely, but you’ve captured the recursive structure now: try creating an instance now!

Student: OK…

```java
interface Post {}
record Repost(String message, Post original) { }
record RegularPost(String message) { }
Post r = new Repost("what he said",
          new Repost("what she said",
            new RegularPost("I love to post")));
```

Output (compile error):

```text
line 4: error: The constructor Repost(String, Repost) is undefined
line 4: error: Type mismatch: cannot convert from Repost to Post
line 5: error: The constructor Repost(String, RegularPost) is undefined
```

Student: Wait, why didn’t that work?

Prof: This is an important detail: there are two uses of the `Repost` constructor in your program. One of them is taking a `RegularPost`, and the other is taking a `Repost`. But neither of those are `Post` values according to Java!

Student: Huh? I wrote the interface right there!

Prof: Do you remember anything from `ImageQuery` about something we need to add to record definitions?

Student: Oh! I need to say `implements`? Why?

Prof: Well, it’s how we tell Java “I want all `Repost` objects to count as `Post` objects; **and** I want all `RegularPost` objects to count as `Post` objects. It’s also one of the **only** ways to get this kind of sharing of classes with one type in Java.

Student: So without `implements`, there can never be a way to have `Repost` be a `Post`?

Prof: That’s right. Let’s fix it!

```java
interface Post {}
record Repost(String message, Post original) implements Post { }
record RegularPost(String message) implements Post { }
Post r = new Repost("what he said",
          new Repost("what she said",
            new RegularPost("I love to post")));
```

Output:

```text
r = Repost[message=what he said, original=Repost[message=what she said, original=RegularPost[message=I love to post]]]
```

Prof: Nice! Let’s look at the memory diagram.

```
Names (the stack)
  top level
    r = @1003
Heap
  @1001: RegularPost[message=I love to post]
  @1002: Repost[message=what she said, original=@1001]
  @1003: Repost[message=what he said, original=@1002]
```

Student: You know, this does just kind of look like nested data.

Prof: That’s a good observation. There’s a big difference between what you can create with something like your `Post`, `Repost`, and `RegularPost`, though. You can make a chain of `Repost` instances **as long as you want**. With types that describe just nested data, not recursive data, it always has to stop at some point. We’ll explore why that’s special by writing some recursive methods next.

## [Recursive Methods](recursive-methods.html)

Student: How do I know how to make methods for recursive data?

Prof: It can take a little practice! But the split of base case and recursive case helps a lot. The idea is that we implement the method in each class that is part of our recursive data definition – this is called structural recursion specifically, and it matches the examples we’ve seen so far.

Student: So to implement a method I have to implement the same method over and over?

Prof: Kind of! And we’ve seen this a few times. Like for the `matches` method, we had a method body for `HasExtension`, and a method body for `HasKeyword`, and a method body for `Or`, and so on. Each one handled just the behavior specific to its class. In the case of recursive cases like `Or`, it called the same method on its pieces to get its result.

```java
interface ImageQuery { boolean matches(ImageData im); }
record HasExtension(String ext) implements ImageQuery {
  public boolean matches(ImageData im) { ... ext ... }
}
record HasKeyword(String keyword) implements ImageQuery {
  public boolean matches(ImageData im) { ... keyword ... }
}
record Or(ImageQuery q1, ImageQuery q2) implements ImageQuery {
  public boolean matches(ImageData im) { ... q1.matches(im) ... q2.matches(im) ... }
}
record And(ImageQuery q1, ImageQuery q2) implements ImageQuery {
  public boolean matches(ImageData im) { ... q1.matches(im) ... q2.matches(im) ... }
}
```

Prof: The same kind of shape is true of `Pict`

```java
interface Pict { int width(); /* plus many more methods */ }
record Circle(int radius, String color) implements Pict {
  public int width() { ... radius ... }
}
record Rect(int width, int height, String color) implements Pict {
  public int width() { ... width ... }
}
record Beside(Pict left, Pict right) implements Pict {
  public int width() { ... left.width() ... right.width() ... }
}
record Above(Pict top, Pict bottom) implements Pict {
  public int width() { ... top.width() ... bottom.width() ... }
}
```

Student: Hey, you left out a lot of detail in these!

Prof: That’s on purpose – I want to illustrate a **common shape** between these. In all the base cases, the methods worked with just the parameters of the method, and the fields of the class. So `width` for a `Circle` uses the `radius`, `matches` for `HasKeyword` uses the `keyword`, and so on. In contrast the recursive cases make recursive calls using the same-named method on their pieces. It’s a general pattern!

```java
interface RecursiveData { Type recMethod(Param p, ...); }
record BaseCase(Field field, ...) implements RecursiveData {
  public Type recMethod(Param p, ...) { ... field ... }
}
record RecCase(Field field, ... RecursiveData d, ...) implements RecursiveData {
  public Type recMethod(Param p, ...) { ... field ... d.recMethod(p, ...) ... }
}
// Could be several different BaseCase and RecCase classes for a recursive data
// definition, not just base and rec
```

Student: Hmmm I think I’m starting to see. So the recursive case will always have a **field** that refers back to the interface?

Prof: That’s right. Think you can apply it to your `Post` now?

Student: So I already have the outline of my base case and my recursive case. I need to pick a method to try. Maybe like… if a word shows up anywhere in the chain of reposts? Like a search?

Prof: Sounds like a good example. It’s useful to think about the base case first. Actually, before that, let’s think about a few examples. You had the example with two reposts and a regular post. What else should we test?

Student: Probably a regular post on its own?

Prof: Sounds like a good idea. Let’s get that down with placeholder values as answers.

How do we check if a word is in a post chain that’s **just** a regular post? Like what should the answer be for `hasWorld`, and how do we calculate it from `word` and `message`?

Prof: Let’s try going from the pattern we had before. What does the pattern tell us should show up in the recursive method?

Student: Hmm well I guess… a recursive call?

Prof: And what would that recursive call look like in this case?

Student: I guess like… hmm.. like `original.hasWord(word)`. So the pattern is like


Prof: Right! And what does that recursive call tell you? Describe it.

Student: It’s, I guess a boolean. And it always returns `false` right now.

Prof: Ah, right, so this is important. When we write a recursive method, we need to trust ourselves a little bit. Say we trust ourselves that `hasWord` is going to be implemented perfectly. **Then** what does the return value of `original.hasWord` mean?

Student: It’s whether the word appears in the original’s `message`. Oh wait, no, whether it appears in the whole chain starting at `original`?

Prof: Indeed! And then we need to combine that information with information about this `Repost`. The word appears if it appears in **either** the `message` of this `Repost` **or** in the chain that starts with `original`.

Student: So I combine them with `||` to get the answer?

Prof: Try it!

```java
interface Post {
  boolean hasWord(String word);
}
record Repost(String message, Post original) implements Post {
  public boolean hasWord(String word) {
    return message.contains(word) || original.hasWord(word);
  }
}
record RegularPost(String message) implements Post {
  public boolean hasWord(String word) { return message.contains(word); }
}
Post reg = new RegularPost("Hello world!");
Post r = new Repost("what he said",
          new Repost("what she said",
            new RegularPost("I love to post")));
boolean hasWorld = reg.hasWord("world");
boolean hasPotato = reg.hasWord("potato");
boolean hasPost = r.hasWord("post");
boolean hasSaid = r.hasWord("said");
boolean hasThey = r.hasWord("they");
```

Output:

```text
reg = RegularPost[message=Hello world!]
r = Repost[message=what he said, original=Repost[message=what she said, original=RegularPost[message=I love to post]]]
hasWorld = true
hasPotato = false
hasPost = true
hasSaid = true
hasThey = false
```

Student: Whoa, that worked.

Prof: Pretty cool, right?

## [A Universal Base Case](null.html)

Student: My friend figured out how to make recursive data without an interface.

Prof: Oh really?

Student: Well, actually it was AI again. But I was trying to figure out some of this recursive data stuff, and it made a program that had `null` in it:

```java
record Person(String name, Person parent1, Person parent2) { }
Person p = new Person("Bob", new Person("Brenda", null, null), null);
```

Output:

```text
p = Person[name=Bob, parent1=Person[name=Brenda, parent1=null, parent2=null], parent2=null]
```

Student: It looks like it uses `null` everywhere we would have had a base case like `Unknown`.

Prof: Ah I see. Yes, you can do this! Java will let you store `null` in a field or variable or parameter of any reference type. So `null` can be stored in a `Person` field.

Student: So why don’t we just use that all the time?

Prof: You can, but it requires using a different style. The main reason is I like having the base case classes to put methods in. For example, if we want to have a `oldestKnownGeneration` method, how do we do that? Try to write it inside `Person`.

Student: Ummm, let’s see, we need to check if either parent is `null` right? And if they are, then we return `1`, because there’s nothing more to visit.

```java
record Person(String name, Person parent1, Person parent2) {
  int oldestKnownGeneration() {
    if(parent1 == null && parent2 == null) { return 1; }
    int oldestParents = Math.max(parent1.oldestKnownGeneration(), parent2.oldestKnownGeneration());
    return 1 + oldestParents;
  }
}
Person p = new Person("Bob", new Person("Brenda", null, null), null);
int oldest = p.oldestKnownGeneration();
```

Output (failed):

```text
Exception in thread "Thread-0" java.lang.NullPointerException
	at Person.oldestKnownGeneration(Unknown Source)
	at <init>(Unknown Source)
```

Student: Wait, why is that an error?

Prof: Let’s look at the trace

```
Names (the stack), over time →
  top level
    p = @1002
    p.oldestKnownGeneration() on @1002
      throws NullPointerException: parent2 is null
      parent1.oldestKnownGeneration() on @1001
        returns 1
Heap
  @1001: Person[name=Brenda, parent1=null, parent2=null]
  @1002: Person[name=Bob, parent1=@1001, parent2=null]
```

Prof: On the person with name `"Bob"`, there’s one parent that’s null and another that isn’t. So we try to call `parent2.oldestKnownGeneration()`, but `parent2` is `null`. That is exactly what `NullPointerException` means: trying to use a field or call a method on the value `null`.

So we’d actually need two checks – one for each parent. Those would be some number, or 0 if null. In my opinion, the code for this gets pretty complex:

```java
record Person(String name, Person parent1, Person parent2) {
  int oldestKnownGeneration() {
    int oldest = 0;
    if(parent1 != null) { oldest = parent1.oldestKnownGeneration(); }
    if(parent2 != null) { oldest = Math.max(oldest, parent2.oldestKnownGeneration()); }
    return 1 + oldest;
  }
}
Person p = new Person("Bob", new Person("Brenda", null, null), null);
int oldest = p.oldestKnownGeneration();
```

Output:

```text
p = Person[name=Bob, parent1=Person[name=Brenda, parent1=null, parent2=null], parent2=null]
oldest = 2
```

Student: Huh. How did you know to do both of those checks?

Prof: Lots of experience. It’s not clear to me in all cases how to structure this code. I find the structural definition works better. Plus, this example had a clear “empty” case – when the ancestor is unknown. In other cases, like your `Post`, the base case actually has information in it, like the message of a `RegularPost`.

Student: Hmm, OK. So sometimes we can use `null` for base cases?

Prof: I think you **can**, but it’s not clear how often you **should**. And `NullPointerException` is not a fun one to get. My advice is to try to write `null`-free programs! And if you see `null` come up in a recursive program you’re reading, try to think of it like a base case class.

Student: Huh. I’ll think about that.
