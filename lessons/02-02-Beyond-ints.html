Short answer

So far, all the fields we’ve defined have held ints, as have all the calculations we’ve done. But Java, and programming languages in general, support many other kinds of data. A common instance of data is a String, which is a sequence of characters. Strings can represent a wide variety of information – names of people or places, addresses, passwords, usernames, web site addresses, the content of a paragraph like this one, and more.

In Java, we create Strings by putting a sequence of characters in between quotation marks. Strings can be stored in fields, just as ints can, though there’s an important difference in how we write down those fields:

class StringExamples {
  String name = "Dorothy Vaughan";
  String password = "s00peR_C_kret";
  String sentence = "But Java, and programming languages in general, support many other kinds of data.";
}

See the difference? Instead of writing int, we write String before the name of the field.

(You might have noticed that String starts with a capital S, but int starts with a lowercase i. We'll discuss why this is later on.)

Since a String consists of a sequence of characters, sometimes we might also want to consider how many characters are in a given String. The quotation marks are part of the way we write out String values, but these quotation marks are not included in the length. The length of the String is determined by the number of characters in between the quotes, including spaces, numbers, and punctuation. For example, "Eritrea" contains 7 characters, and "s00peR_C_kret" contains 13 characters.

Short answer
Oh no! We wanted to add the numeric values of the prices, but by representing the prices as Strings, using the + operator concatenated them instead! The + operator works as we desire for int fields, but the prices are not integers! What can we do?



Fortunately, Java has many more data types we can utilize. Here's a brief summary of all primitive data types in Java:



    
	
  • byte: Represent integers from -128 through 127
    • 
	
  • short: Represent integers from -32,768 through 32,767
    • 
	
  • int: Represent integers from -2,147,483,648 through 2,147,483,647
    • 
	
  • long: Represent integers from -9,223,372,036,854,775,808 through 9,223,372,036,854,775,807
    • 
	
  • float: Represent decimal numbers with up to 6 or 7 digits
    • 
	
  • double: Represent decimal numbers with up to 15 or 16 digits
    • 
	
  • boolean: Represent true or false values
    • 
	
  • char: Represent a single character/letter (a String can be thought of as a collection of chars)
    • 




For representing numbers, the Java documentation recommends using int to represent integer numbers and double to represent decimal numbers. If you're curious, you can read more about Java's primitive data types in the Primitive Data Types article of the Java documentation.

Where did all of those additional decimal places come from? If you were curious and read the Primitive Data Types article in the Java documentation as we suggested, you may have stumbled upon the following description for the double data type:





The double data type is a double-precision 64-bit IEEE 754 floating point. Its range of values is beyond the scope of this discussion, but is specified in the Floating-Point Types, Formats, and Values section of the Java Language Specification. For decimal values, this data type is generally the default choice. As mentioned above, this data type should never be used for precise values, such as currency.





In Java, the integer types (byte, short, int, and long) are precise. For example, if we create an int variable with the value 42 (e.g. int x = 42;), the variable stores exactly the value 42. However, the floating point types (float and double) have limited precision. For example, when we think of the number 49.99, we actually are thinking of the value 49.9900000000... (with an infinite number of 0s). However, because Java's floating point types have limited precision, the number 49.99 is only precise to a certain number of decimal digits.



A thorough discussion about floating point precision, while surely interesting (sarcasm), is a bit out of the scope of this text.
